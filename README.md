# ระบบ Demo ร้านขายยาออนไลน์ (Term Project วิชา Database)

Flask + python-oracledb + Bootstrap บน Oracle XE 21c
ชื่อตารางและคอลัมน์ทั้งหมดมาจาก `sql/01_schema.sql` (สำเนาของ `D:\Database\pharmacy_schema_final_oracle.sql` ไม่ได้แก้ไข)
ส่วนที่ต่างจาก DDL ต้นฉบับอยู่ใน `migrations/` (ต้องรันหลัง `01_schema.sql`)

## โครงสร้างไฟล์

| ไฟล์ | หน้าที่ |
|---|---|
| `transactions.py` | **ส่วนที่ใช้อธิบายตอนนำเสนอ** : ทุก INSERT/UPDATE, COMMIT/ROLLBACK (`request_consult`, `issue_prescription`, `place_order`, `pay_order`) |
| `app.py` | หน้าจอ, SELECT, API สำหรับ polling |
| `db.py` | connection pool และตัวช่วย SELECT |
| `sql/00_create_user.sql` | สร้าง schema `pharmacy_demo` (รันครั้งเดียวด้วย SYSDBA) |
| `sql/01_schema.sql` | DDL 24 ตาราง |
| `migrations/001_orders_rejected.sql` | `orders.status` รับค่า `rejected`, `uq_orders_prescription` เป็น unique index แบบมีเงื่อนไข |
| `migrations/003_drop_symptom_note.sql` | ลบ `consult_queue.symptom_note` ถ้ามี (คอลัมน์ที่เคยเพิ่มแล้วยกเลิก ตารางคิวตรงกับ `01_schema.sql`) |
| `migrate.bat` | รันทุกไฟล์ใน `migrations/` ตามลำดับ (รันซ้ำได้ ไม่ลบข้อมูล) |
| `sql/seed.sql` | ข้อมูลตั้งต้น: ร้านยา 1 ร้าน (ร้านขายยาแมนนี่จัง), เภสัชกร 2 คน, คนไข้ 4 คน (วีระเป็น VIP), ยา 6 รายการ (ยา A = 20) |
| `sql/reset.sql`, `reset.bat` | ล้างข้อมูลที่ซ้อม คืนสต็อก คืนค่าร้านของเภสัชกรและสถานะ VIP |
| `sql/demo_queries.sql` | query โชว์ผลหลังทำ Demo |
| `templates/`, `static/app.css`, `static/fonts/` | หน้าจอ (ดีไซน์จาก Stitch), CSS ที่ build จาก Tailwind, ฟอนต์ Prompt/Sarabun/Kanit เก็บในเครื่อง ใช้ได้โดยไม่ต่ออินเทอร์เน็ต |
| `tailwind.config.js`, `static/src/app.css` | ต้นทางสำหรับ build `static/app.css` |
| `stitch_nine_page_design_replicator/` | ไฟล์ดีไซน์ต้นฉบับจาก Stitch (ใช้อ้างอิง แอปไม่ได้โหลด) |
| `static/drugsearch.js` | ช่องค้นหายาแบบ type-ahead ในฟอร์มใบสั่งยา |
| `test_flow.py` | ทดสอบรอบเต็ม + ค้นหายา + ปฏิเสธตอนสั่งซื้อ (ROLLBACK + แถว rejected) + คิวรอ/VIP แซงคิว + ตัวนับเวลาตอบกลับ/หมดเวลาทั้งสองฝ่าย กับฐานข้อมูลจริง |

## ติดตั้ง (ทำครั้งเดียว)

```powershell
cd D:\database_project
python -m pip install -r requirements.txt

$env:NLS_LANG = "AMERICAN_AMERICA.AL32UTF8"      # จำเป็น ไม่งั้นภาษาไทยใน .sql จะเพี้ยน
sqlplus / as sysdba "@sql\00_create_user.sql"
"exit" | sqlplus -S pharmacy_demo/pharmacy_demo@localhost:1521/XEPDB1 "@sql\01_schema.sql"
"exit" | sqlplus -S pharmacy_demo/pharmacy_demo@localhost:1521/XEPDB1 "@sql\seed.sql"
.\migrate.bat                                     # migrations\*.sql (รันซ้ำได้)
```

บนเครื่องนี้ทำทุกขั้นตอนนี้ไปแล้ว (รวม migration) ไม่ต้องทำซ้ำ ถ้าสร้าง schema ใหม่จาก `01_schema.sql` ต้องรัน `migrate.bat` ด้วยทุกครั้ง
ถ้าใช้ SQL Developer ให้สร้าง connection: user `pharmacy_demo`, password `pharmacy_demo`,
hostname `localhost`, port `1521`, **Service name** `XEPDB1` แล้วเปิดไฟล์ .sql กด F5

## หน้าตา (Tailwind) และการแก้ template

หน้าเว็บโหลดเฉพาะ `static/fonts.css` และ `static/app.css` ไม่มีลิงก์ออกอินเทอร์เน็ต
`static/app.css` มีเฉพาะ class ที่ใช้อยู่ใน `templates/` และ `static/*.js`
**ถ้าเพิ่ม class Tailwind ใหม่ใน template ต้อง build ใหม่** (ต้องต่ออินเทอร์เน็ตตอนติดตั้งครั้งแรก):

```powershell
cd D:\database_project
npm install --no-save tailwindcss@3.4.17 @tailwindcss/forms@0.5.9 @tailwindcss/container-queries@0.1.1
npx tailwindcss -c tailwind.config.js -i static/src/app.css -o static/app.css --minify
```

แก้ template แล้วต้องปิดและเปิด `python app.py` ใหม่ เพราะ Flask จำ template ไว้ตอนไม่ได้เปิด debug
ชื่อ id/class ที่ `static/*.js` ใช้ (`chat-box`, `chat-form`, `chat-status`, `d-none`, `msg mine/theirs`, `countdown`,
`drug-search`, `drug-results` ฯลฯ) กำหนดสไตล์ไว้ท้าย `static/src/app.css` ห้ามเปลี่ยนชื่อ

## ลำดับ Demo (3–4 นาที)

เตรียม: รัน `reset.bat`, เปิด `python app.py`, เปิด SQL Developer ที่ `demo_queries.sql`
เปิดหน้าต่าง: คนไข้ (สมหญิง), เภสัชกรสมชาย เป็นหลัก

1. **ก่อนทำ** – หน้าต่างเภสัชกรสมชาย → เมนู "สต็อกยา" : ยา A = 20
2. **ฟังก์ชันหลัก**
   - คนไข้ (สมหญิง) กด "ขอรับคำปรึกษา" ปุ่มเดียว → ระบบสร้างคิวและจับคู่ ภก. สมชาย ให้เอง
     ห้องแชทขึ้นสถานะ "รอตอบกลับ"
   - หน้าเภสัชกรสมชาย "ห้องแชทที่รอตอบกลับ" มีห้องใหม่ขึ้นเองภายใน 2 วินาที พร้อมตัวนับเวลา 10 นาที
     (ไม่มีปุ่มรับคิว) → "เปิดห้องแชท"
   - คนไข้พิมพ์อาการ → เภสัชกรตอบข้อความแรก → สถานะเปลี่ยนเป็น "ระหว่างปรึกษา" ตัวนับเวลาหายไป
3. **ปฏิเสธ + ROLLBACK (ฝั่งคนไข้ตอนสั่งซื้อ)**
   - ในห้องแชทเดิม เภสัชกรกรอกใบสั่งยา 2 รายการ: ลอราทาดีน **5** และ ยา A **25** → "ออกใบสั่งยา" → "ปิดห้องแชท"
     (เลือกยาด้วยช่องค้นหา: พิมพ์ชื่อบางส่วนหรือรหัสยา เช่น `ลอรา`, `พารา`, `1` แล้วกดลูกศร/Enter
     ออกได้แม้ยา A เหลือ 20 เพราะฝั่งเภสัชกรไม่เทียบจำนวนกับคงเหลือ ผลค้นหาแสดง "เหลือ 20" เป็นข้อมูลประกอบ
     ส่วน "คลอร์เฟนิรามีน 4 mg · หมด" เลือกไม่ได้)
   - รัน query ข้อ 9 และ 10 จดตัวเลขไว้ → คนไข้กด "ดูใบสั่งยาและสั่งซื้อ" → "สั่งซื้อ"
     → ขึ้นแถบ "ระบบปฏิเสธรายการ: สต็อกไม่พอ: ยา A (พาราเซตามอล 500 mg) คงเหลือ 20 สั่ง 25 ไม่ได้ ระบบยกเลิกคำสั่งซื้อและคืนสต็อกทั้งหมดแล้ว
     (บันทึกเป็นคำสั่งซื้อเลขที่ 2 สถานะ “ถูกปฏิเสธ”)"
   - รัน query ข้อ 5, 9 และ 10 ซ้ำ : `orders` เพิ่ม 1 แถว `status = rejected` (ร่องรอยว่าคนไข้เคยกดสั่งซื้อ)
     ตารางอื่นเท่าเดิม ไม่มี `order_detail` ของคำสั่งนี้, ยา A = 20 และลอราทาดีน = 100 / 200 เท่าเดิม
     (ลอราทาดีน 5 ถูกหักไปแล้วในบรรทัดที่ 1 แต่ ROLLBACK คืนให้ทั้งหมด)
   - หน้า "ประวัติคำสั่งซื้อ" ของสมหญิงมีแถวป้าย "ถูกปฏิเสธ" และใบสั่งยาเดิมยังกด "สั่งซื้อ" ใหม่ได้เมื่อสต็อกพอ
4. **ทำต่อให้สำเร็จ** – คนไข้กด "ขอรับคำปรึกษา" อีกครั้ง (ห้องแชท 1 ห้องออกใบสั่งยาได้ 1 ใบ)
   ครั้งนี้ระบบจับคู่ ภก. อีกคน (เปิดหน้าต่างเภสัชกรคนที่ 2) → ตอบ 1 ข้อความ → ออกใบสั่งยา ยา A จำนวน **2** → "ปิดห้องแชท"
   - คนไข้กด "ดูใบสั่งยาและสั่งซื้อ" → ตรวจที่อยู่ → "สั่งซื้อ" → กดจำลอง QR → เห็นใบเสร็จ
5. **หลังทำ** – รัน `demo_queries.sql` : มีแถวใหม่ทุกตาราง, ยา A = 18
6. **ผลลัพธ์ปลายทาง** – หน้า "สต็อกยา" (ยา A = 18 พร้อมเวลาตัดสต็อก) และ
   "ประวัติคำสั่งซื้อ" ของสมหญิง (สถานะ ชำระเงินแล้ว + เลขที่ใบเสร็จ)

### ถ้ามีเวลา: คิวรอจริง + VIP แซงคิว (ราว 1 นาที)

เปิดหน้าต่างคนไข้ 4 คน และเภสัชกร 2 คน

1. สมหญิง และ ธนากร กด "ขอรับคำปรึกษา" → ได้เภสัชกรคนละคน (เภสัชกรเต็มทั้งสองคน)
2. มาลี (ทั่วไป) กด → ขึ้น "รอจับคู่ ลำดับที่ 1 ในคิว" ไม่มีห้องแชท
3. วีระ (VIP) กด → วีระได้ "ลำดับที่ 1" และหน้าของมาลีเปลี่ยนเป็น "ลำดับที่ 2" เองภายใน 2 วินาที
   (รัน query ข้อ 2.2 ใน `demo_queries.sql` เห็นลำดับเดียวกัน)
4. เภสัชกรคนหนึ่งตอบ 1 ข้อความแล้วกด "ปิดห้องแชท" → วีระได้ห้องกับเภสัชกรคนนั้นทันที
   มาลีเลื่อนเป็นลำดับที่ 1
5. เภสัชกรอีกคนกด "ทดสอบ: หมดเวลา" → ห้องเป็น "ให้คำปรึกษาไม่สำเร็จ" และมาลีได้ห้องต่อทันที
6. ในห้องแชทของมาลี: เภสัชกรตอบ 1 ข้อความ → ฝั่งคนไข้ขึ้น "ต้องตอบภายใน 05:00" →
   กด "ทดสอบ: คนไข้หมดเวลา" → ห้องเป็น "ปิดห้องแชทแล้ว" พิมพ์ต่อไม่ได้

### ถ้ามีเวลา: สต็อกลดลงหลังออกใบสั่งยา และยาหลายล็อต (ROLLBACK ตอนสั่งซื้อ)

- ออกใบสั่งยา ยา A ให้คนไข้ 2 คน คนละ 10 (ตอนออกยังเหลือ 18) คนแรกสั่งซื้อ → เหลือ 8
  → คนที่สองกด "สั่งซื้อ" → "สต็อกไม่พอ: ยา A … คงเหลือ 8 สั่ง 10 ไม่ได้ ระบบยกเลิกคำสั่งซื้อและคืนสต็อกทั้งหมดแล้ว"
- ออกใบสั่งยา ลอราทาดีน 250 (เหลือ 90 + 200 = 290) → คนไข้กด "สั่งซื้อ" →
  "ลอราทาดีน 10 mg คงเหลือรวม 290 แต่ไม่มีล็อตเดียวที่มีจำนวนพอสำหรับ 250 (ล็อตที่มากที่สุดมี 200) …"
- รัน query ข้อ 9 และ 10 ซ้ำ : สต็อกไม่เปลี่ยน และมีเพียง `orders` ที่เพิ่ม 1 แถว (`rejected`) ต่อการปฏิเสธ 1 ครั้ง

## ขั้นตอนการปรึกษาและสถานะ

| เหตุการณ์ | `consult_queue.status` | `chat_room.status` | สถานะที่แสดง (ตามรายงาน) |
|---|---|---|---|
| คนไข้กดขอรับคำปรึกษา เภสัชกรเต็มทุกคน | `waiting` | (ยังไม่มีห้อง) | รอจับคู่ + ลำดับที่ในคิว |
| มีเภสัชกรว่าง ระบบจับคู่และสร้างห้อง | `in_progress` | `open` | รอตอบกลับ |
| เภสัชกรส่งข้อความแรก | `in_progress` | `open` | ระหว่างปรึกษา |
| เภสัชกรกดปิดห้องแชท | `completed` | `closed` | ปิดห้องแชทแล้ว |
| เภสัชกรไม่ตอบภายใน 10 นาที | `cancelled` | `closed` | ให้คำปรึกษาไม่สำเร็จ |
| คนไข้ไม่ตอบภายใน 5 นาที | `completed` | `closed` | ปิดห้องแชทแล้ว |

- DDL ให้ `chat_room.status` มีแค่ `open` / `closed` จึง **ไม่แก้ DDL** สถานะตามรายงานคำนวณจาก
  สถานะห้อง + มีข้อความจากเภสัชกรหรือยัง + สถานะคิว (`CHAT_STATE_SQL` ใน `transactions.py`)
- เภสัชกร 1 คนถือห้อง `open` ได้พร้อมกันไม่เกิน `MAX_OPEN_CHATS` (= 1) แก้ได้ที่ต้นไฟล์ `transactions.py`
- จับคู่ (`_match_waiting`) = คิว `waiting` ลำดับแรก กับเภสัชกรที่ว่างและถือห้องน้อยที่สุด
  (ถ้าเท่ากันเลือกคนที่ได้ห้องล่าสุดนานที่สุด) ถ้าทุกคนเต็ม คิวรอต่อโดยไม่มีห้องแชท
- ลำดับในคิว (`QUEUE_ORDER_SQL`): VIP ก่อนสมาชิกทั่วไป แล้วตามเวลาเข้าคิว
  `member_type` ของคิวมาจาก `patient.is_vip` ตอนกดขอ
- การจับคู่เกิด 3 จังหวะ และอยู่ใน Transaction เดียวกับเหตุการณ์นั้นเสมอ:
  ตอนขอรับคำปรึกษา (`request_consult`), ตอนปิดห้อง (`close_chat`), ตอนหมดเวลา (`expire_unanswered`)
- หน้าหลักคนไข้ polling ทุก 2 วินาที ลำดับที่ในคิวจึงอัปเดตเองเมื่อมีคนแซงหรือคิวข้างหน้าได้ห้อง
- ระบบมีร้านยาร้านเดียว ระบบใส่ `pharmacy_id` ให้เอง ไม่มีหน้าเลือกร้าน และไม่แสดงชื่อร้านบนหน้าจอ
  ยกเว้นใบเสร็จ ซึ่งต้องมีชื่อร้าน ที่อยู่ และเลขใบอนุญาต
- ปิดห้องแชทได้เมื่อเภสัชกรตอบแล้วอย่างน้อย 1 ข้อความ ออกใบสั่งยาได้ห้องละ 1 ใบขณะห้องยังเปิด

## ตัวนับเวลาตอบกลับ

ตัวนับเริ่มใหม่ทุกครั้งที่มีข้อความ คำนวณจากข้อความล่าสุดของห้องใน `chat_message` (`sender_type`, `sent_at`)
ไม่ได้เพิ่มคอลัมน์หรือแก้ DDL (`TURN_SQL`, `SECONDS_LEFT_SQL` ใน `transactions.py`)

| ข้อความล่าสุดของห้อง | ฝ่ายที่ต้องตอบ | เวลา | นับจาก | ถ้าไม่ตอบทัน |
|---|---|---|---|---|
| ยังไม่มีข้อความ | เภสัชกร | 10 นาที | `chat_room.started_at` (เวลาที่จับคู่) | ให้คำปรึกษาไม่สำเร็จ (คิว `cancelled`) |
| มาจากคนไข้ | เภสัชกร | 10 นาที | `sent_at` ของข้อความนั้น | ให้คำปรึกษาไม่สำเร็จ (คิว `cancelled`) |
| มาจากเภสัชกร | คนไข้ | 5 นาที | `sent_at` ของข้อความนั้น | ปิดห้องแชทแล้ว (คิว `completed`) |

- ตั้งเวลาได้ที่ `PHARMACIST_REPLY_MINUTES` และ `PATIENT_REPLY_MINUTES`
- หน้าแชททั้งสองฝั่งมีตัวนับ: ฝ่ายที่ต้องตอบเห็น "ต้องตอบภายใน mm:ss" อีกฝ่ายเห็น "รอเภสัชกร/คนไข้ตอบกลับ mm:ss"
  ค่ามาจากเซิร์ฟเวอร์ทุกรอบ polling (1.5 วินาที) จึงรีเซ็ตเองเมื่อมีข้อความใหม่
- หน้ารายการห้องของเภสัชกร: ตาราง "ห้องแชทที่รอตอบกลับ" คือห้องที่รอเภสัชกรตอบ (รวมห้องระหว่างปรึกษาที่คนไข้เพิ่งส่งข้อความ)
  ห้องที่รอคนไข้ตอบอยู่ในตารางล่างพร้อมตัวนับ "รอคนไข้ตอบ"
- **ตรวจเวลาฝั่งเซิร์ฟเวอร์ทุกครั้งที่ส่งข้อความ** (`send_message`): ถ้าฝ่ายที่ต้องตอบเกินเวลาแล้ว ข้อความถูกปฏิเสธ
  ห้องถูกปิด และคิวที่รอคนถัดไปได้ห้อง ทั้งหมดใน Transaction เดียว นอกจากนี้ polling ก็ปิดห้องที่เกินเวลาให้เอง (`expire_overdue`)
- ปุ่มทดสอบสำหรับ Demo: ในหน้าแชททั้งสองฝั่งมีปุ่ม "ทดสอบ: เภสัชกรหมดเวลา" หรือ "ทดสอบ: คนไข้หมดเวลา"
  (เปลี่ยนตามฝ่ายที่ต้องตอบอยู่ตอนนั้น) และหน้ารายการห้องของเภสัชกรมีปุ่ม "ทดสอบ: หมดเวลา" ต่อห้อง
- ข้อจำกัด: ห้องที่ปิดเพราะคนไข้ไม่ตอบ กับห้องที่เภสัชกรกดปิดเอง มีค่าในฐานข้อมูลเหมือนกัน
  (`closed` + `completed`) จึงแสดงเป็น "ปิดห้องแชทแล้ว" เหมือนกัน

## การกันสต็อก (ตัวหลักอยู่ที่ตอนคนไข้สั่งซื้อ)

| จุด | เมื่อไร | ตรวจอะไร | ถ้าไม่ผ่าน |
|---|---|---|---|
| `issue_prescription` | เภสัชกรกดออกใบสั่งยา | ยาที่คงเหลือรวม 0 (หมด), จำนวนเป็นจำนวนเต็มมากกว่า 0, กรอกขนาดยา/วิธีใช้ครบ | ไม่สร้างใบสั่งยา แสดง error ที่หน้าเภสัชกร |
| `place_order` **(ตัวหลัก)** | คนไข้กดสั่งซื้อ | จำนวนที่สั่งเทียบกับสต็อก (จ่ายจากล็อตเดียวต่อรายการ แบบ FEFO) | ROLLBACK ทั้งคำสั่งซื้อ แล้วบันทึก `orders` สถานะ `rejected` 1 แถว แสดงเหตุผลที่หน้าคนไข้ |

- ฝั่งเภสัชกร **ไม่เทียบจำนวนที่สั่งกับคงเหลือ** : ออกใบสั่งยาเกินคงเหลือได้ ช่องค้นหายาแสดง "เหลือ N" เป็นข้อมูลประกอบ
  ยาที่คงเหลือรวม 0 แสดง "หมด" เลือกไม่ได้ และเซิร์ฟเวอร์ปฏิเสธซ้ำอีกชั้น
- ตอนสั่งซื้อ ถ้ายารายการใดตัดสต็อกไม่ได้ ระบบ ROLLBACK ทั้งใบ รวมคืนสต็อกของรายการก่อนหน้าที่หักไปแล้ว
- ข้อความปฏิเสธใช้คงเหลือรวมของยา (ทุกล็อตที่ยังไม่หมดอายุ ตัวเลขเดียวกับช่องค้นหายาและหน้าสต็อกยา) เทียบกับจำนวนที่สั่ง
  (`_raise_out_of_stock`):
  - คงเหลือรวมไม่พอ → "สต็อกไม่พอ: ยา A … คงเหลือ 20 สั่ง 25 ไม่ได้ ระบบยกเลิกคำสั่งซื้อและคืนสต็อกทั้งหมดแล้ว"
  - คงเหลือรวมพอ แต่ไม่มีล็อตใดพอ (เช่น ลอราทาดีน 90 + 200 สั่ง 250) →
    "สต็อกไม่พอ: ลอราทาดีน 10 mg คงเหลือรวม 290 แต่ไม่มีล็อตเดียวที่มีจำนวนพอสำหรับ 250 (ล็อตที่มากที่สุดมี 200) ระบบยกเลิกคำสั่งซื้อและคืนสต็อกทั้งหมดแล้ว"

### ร่องรอยของคำสั่งซื้อที่ถูกปฏิเสธ (`orders.status = 'rejected'`)

- `_run()` ROLLBACK งานหลักเหมือนเดิม แล้ว **เฉพาะกรณีระบบปฏิเสธ** (`RejectedError` : สต็อกไม่พอ จาก `_raise_out_of_stock`
  หรือ error จากฐานข้อมูล) จะเปิด Transaction ใหม่บน connection ใหม่ INSERT `orders` 1 แถว สถานะ `rejected`
  (คนไข้ ใบสั่งยา ที่อยู่ที่กรอก) แล้ว COMMIT ไม่มี `order_detail` และไม่ตัดสต็อก เหตุผลไม่ได้เก็บในฐานข้อมูล
- ข้อผิดพลาดจากการกรอกข้อมูล (`DemoError` ธรรมดา : ที่อยู่ว่าง/ยาวเกิน 500, ไม่พบใบสั่งยา, ใบสั่งยาถูกสั่งไปแล้ว) ไม่ถูกบันทึก
- ถ้า INSERT แถว rejected เองล้มเหลว ระบบ log ไว้แล้ว raise error เดิมต่อ (ผู้ใช้ยังเห็นเหตุผลเดิม)
- `uq_orders_prescription` เป็น unique index บน `CASE WHEN status <> 'rejected' THEN prescription_id END`
  ใบสั่งยา 1 ใบจึงมีคำสั่งซื้อจริงได้ใบเดียวเหมือนเดิม แต่มีแถว rejected ได้หลายแถว และสั่งซื้อใหม่ได้เมื่อสต็อกพอ
- ทุกหน้าที่ผูกใบสั่งยากับคำสั่งซื้อ JOIN เฉพาะ `status <> 'rejected'` แถว rejected จึงไม่ไปโผล่เป็น "รอชำระเงิน"
  ชำระเงินไม่ได้ ไม่มีใบเสร็จ และแสดงในหน้า "ประวัติคำสั่งซื้อ" เป็นป้าย "ถูกปฏิเสธ"
- เลขที่คำสั่งซื้อมาจาก `seq_orders` : ครั้งที่ถูกปฏิเสธใช้ไป 2 เลข (เลขที่ถูก ROLLBACK 1 + แถว rejected 1)

## ช่องค้นหายา (ฟอร์มใบสั่งยาของเภสัชกร)

- พิมพ์ในช่องเดียว ค้นได้ทั้งชื่อยา (ค้นกลางคำ ไม่สนตัวพิมพ์) และรหัสยา (ขึ้นต้นด้วย) : `GET /api/pharmacist/<id>/drugs?q=`
  (`search_drugs` ใน `app.py`) คืนไม่เกิน 10 รายการ เรียงตามชื่อ แสดงเป็น "รหัส · ชื่อยา · สต็อกคงเหลือ"
- ใช้ bind variable (`:q`) เท่านั้น และ escape `%` `_` `\` ด้วย `LIKE ... ESCAPE '\'` ถ้า `q` ว่างคืนรายการว่าง
  (ยอมให้ค้นตั้งแต่ 1 ตัวอักษร เพราะรหัสยาในระบบเป็นเลขหลักเดียว)
- `static/drugsearch.js` : เรียก API หลังหยุดพิมพ์ 250 ms, ยกเลิกคำขอเก่าที่ค้างอยู่ (AbortController),
  ลูกศรขึ้น/ลงเลื่อน, Enter เลือก, Esc ปิด ถ้าพิมพ์ไว้แต่ไม่ได้เลือกยาจากรายการ ฟอร์มจะไม่ถูกส่ง
- ไม่ตัดข้ามหลายล็อต เพราะ `prescription_detail.batch_id` เก็บล็อตที่จ่ายได้ล็อตเดียวต่อรายการ (ไม่แก้ DDL)

## ตรรกะฐานข้อมูลโดยย่อ

- **สต็อกอยู่ที่ `drug_batch`** (ยา 1 ตัวมีหลายล็อต) ไม่ใช่ตาราง `drug`
- **สั่งซื้อ = 1 Transaction** (`place_order`): INSERT `orders` → ต่อรายการ: เลือกล็อตแบบ FEFO
  (ยังไม่หมดอายุ, มีพอ, หมดอายุเร็วสุด) → `UPDATE drug_batch ... WHERE quantity >= :quantity`
  → ถ้า rowcount = 0 หรือไม่มีล็อตที่พอ ให้ ROLLBACK ทั้งหมด → INSERT `order_detail` (snapshot ชื่อ/ราคา)
  → บันทึก `prescription_detail.batch_id`
  (ถ้าถูก ROLLBACK เพราะระบบปฏิเสธ `_run()` บันทึกแถว `rejected` ใน Transaction ใหม่ ดูหัวข้อด้านบน)
- **ชำระเงิน = 1 Transaction** (`pay_order`): INSERT `payment` + `qr_code`/`transfer_slip`
  → `UPDATE orders SET status='paid' WHERE status='pending_payment'` → INSERT `receipt` + `receipt_detail`
- ทุก query ใช้ bind variable, id มาจาก SEQUENCE ใน DDL
- จ่ายยาจากล็อตเดียวต่อรายการ จำนวนที่สั่งได้จริงต่อรายการจึงไม่เกินจำนวนของล็อตที่มีมากที่สุด

## การปรับปรุงตามคำแนะนำของอาจารย์

หลังนำเสนอ/รับคำแนะนำ ทีมปรับระบบ 2 เรื่อง ส่วนอื่นของระบบ (รวมระบบคิวปรึกษา) คงเดิม

### 1. ช่องค้นหายา (แทน dropdown) — ฝั่งเภสัชกรตอนเขียนใบสั่งยา

**ปัญหาเดิม:** เลือกยาจาก dropdown ถ้ามียาหลายชนิดจะหายาไม่เจอ

**สิ่งที่แก้:**
- เปลี่ยนเป็นช่องพิมพ์ค้นหาแบบ type-ahead: พิมพ์แล้วแสดงรายการยาที่ตรงกันทันที (หน่วงประมาณ 250 ms หลังหยุดพิมพ์ ยกเลิกคำขอเก่าที่ยังค้าง)
- ค้นได้ทั้ง **ชื่อยา** (ตรงกลางคำก็ได้) และ **รหัสยา** ในช่องเดียว
- แสดงผลสูงสุด 10 รายการ เป็น "รหัส · ชื่อยา · สต็อกคงเหลือ" (นับเฉพาะล็อตที่ยังไม่หมดอายุ)
- ใช้ลูกศรขึ้นลงเลือก Enter ยืนยัน Esc ปิด
- ฝั่งฐานข้อมูลใช้ bind variable และ escape อักขระพิเศษ (`%`, `_`) จึงป้องกัน SQL injection ได้

**ไฟล์ที่เกี่ยวข้อง:** `static/drugsearch.js` (ใหม่), `app.py` (API ค้นหายา), `templates/prescription.html`
**โครงสร้างฐานข้อมูล:** ไม่เปลี่ยน

### 2. กรณีระบบปฏิเสธคำสั่งซื้อ — บันทึกเป็นสถานะ `rejected` แทนการหายเงียบ

**ปัญหาเดิม:** ถ้าสั่งซื้อไม่ผ่าน (เช่น สต็อกไม่พอ) ระบบ ROLLBACK ทั้งหมด ทำให้ในฐานข้อมูล **ไม่เหลือร่องรอยเลยว่าคนไข้เคยกดสั่งซื้อ**

**สิ่งที่แก้:**
- งานหลักยัง ROLLBACK เหมือนเดิม (สต็อกไม่ถูกตัด ไม่มีรายการสั่งซื้อค้าง)
- จากนั้นระบบเปิด transaction ใหม่ บันทึกแถวใน `orders` ด้วยสถานะ **`rejected`** แล้ว COMMIT เพื่อเป็นหลักฐานว่าคนไข้กดสั่งแล้วแต่ถูกปฏิเสธ
- บันทึกเฉพาะกรณีที่ระบบปฏิเสธ (สต็อกไม่พอ, ผิด CHECK/FK) ไม่บันทึกกรณีกรอกข้อมูลผิด (ที่อยู่ว่าง, ใบสั่งยาถูกสั่งไปแล้ว)
- หน้าเว็บแสดงเหตุผลที่ถูกปฏิเสธ และมีป้าย "ถูกปฏิเสธ" ในประวัติคำสั่งซื้อ
- คนไข้สั่งซื้อใหม่จากใบสั่งยาเดิมได้ เพราะคำสั่งซื้อที่ถูกปฏิเสธไม่ล็อกใบสั่งยา

**การเปลี่ยนในฐานข้อมูล** (`migrations/001_orders_rejected.sql`):
- เพิ่มค่า `'rejected'` ใน CHECK ของสถานะ (`chk_orders_status`)
- เปลี่ยน `uq_orders_prescription` จาก UNIQUE เดิมเป็น unique index แบบมีเงื่อนไข เพื่อให้ 1 ใบสั่งยามีคำสั่งซื้อที่ไม่ถูกปฏิเสธได้ไม่เกิน 1 รายการ:
```sql
  CREATE UNIQUE INDEX uq_orders_prescription
    ON orders (CASE WHEN status <> 'rejected' THEN prescription_id END);
```
- คิวรีที่ตรวจ "ใบสั่งยาถูกสั่งไปแล้ว" และหน้ารอชำระเงิน/ใบเสร็จ ไม่นับแถว `rejected`

**ไฟล์ที่เกี่ยวข้อง:** `transactions.py` (`RejectedError`, `_run`, `_record_rejected_order`, ปรับ `place_order` 2 จุด), `app.py`, `templates/orders.html`, `templates/patient_home.html`, `migrations/001_orders_rejected.sql`

### สิ่งที่ไม่ได้เปลี่ยน
- ระบบคิวปรึกษา (จับคู่เภสัชกรอัตโนมัติ, VIP ก่อน, เภสัชกรคนละ 1 ห้อง)
- ลำดับขั้นตอนของ `place_order` ขั้น (1)–(6) (อ่านรายการยา, เช็กสั่งซ้ำ, INSERT orders, เลือกล็อต FEFO, ตัดสต็อกแบบมีเงื่อนไข, บันทึกล็อตที่จ่าย)
- โครงสร้างตารางอื่นทั้งหมด

### วิธีติดตั้งส่วนที่แก้
```
migrate.bat      # รัน migrations\ ทุกไฟล์ตามลำดับ (รันซ้ำได้)
python app.py
```
ถ้าสร้าง schema ใหม่ ให้รัน `sql/01_schema.sql` แล้วตามด้วย `migrate.bat` เสมอ

### วิธีทดสอบกรณีปฏิเสธ
1. ตั้งสต็อกยาให้น้อยกว่าที่ใบสั่งยาขอ (เช่น สต็อก 3 ใบสั่งยา 5)
2. คนไข้กดสั่งซื้อ → หน้าเว็บขึ้นข้อความปฏิเสธ
3. ตรวจในฐานข้อมูล: `orders` มี 1 แถวสถานะ `rejected`, `order_detail` ไม่มีรายการ, `drug_batch.quantity` ยังเท่าเดิม
4. เติมสต็อกแล้วสั่งซ้ำจากใบสั่งยาใบเดิม → ต้องสำเร็จ (ได้แถว `pending_payment` เพิ่ม)

### ข้อสังเกต
- เลขที่คำสั่งซื้อจะข้ามได้ 1 เลขเมื่อมีการปฏิเสธ (Oracle sequence ไม่ย้อนกลับเมื่อ rollback)
- ระบบคิวยังเรียงตามสิทธิ์ VIP แล้วตามเวลาเข้าคิว ตามเหตุผลที่อธิบายไว้ในสไลด์

### 1. ช่องค้นหายา (แทน dropdown) — ฝั่งเภสัชกรตอนเขียนใบสั่งยา

- เปลี่ยนเป็นช่องพิมพ์ค้นหาแบบ type-ahead: พิมพ์แล้วแสดงรายการยาที่ตรงกันใต้ช่อง (หน่วง 250 ms หลังหยุดพิมพ์ ยกเลิกคำขอเก่าที่ยังค้าง)
- ค้นได้ทั้ง **ชื่อยา** (ตรงกลางคำก็ได้ ไม่สนตัวพิมพ์ใหญ่เล็ก) และ **รหัสยา** (ขึ้นต้นด้วย) ในช่องเดียว
- แสดงผลสูงสุด 10 รายการ เรียงตามชื่อยา เป็น "รหัส · ชื่อยา · สต็อกคงเหลือ" (นับเฉพาะล็อตที่ยังไม่หมดอายุ)
  ยาที่คงเหลือ 0 แสดงเป็น "หมด" และเลือกไม่ได้
- ใช้ลูกศรขึ้นลงเลือก Enter ยืนยัน Esc ปิด หรือคลิกที่รายการ
- ฝั่งฐานข้อมูลใช้ bind variable และ escape อักขระพิเศษ (`%`, `_`, `\`) ด้วย `LIKE ... ESCAPE '\'` ถ้าช่องว่างจะคืนรายการว่าง

**ไฟล์ที่เกี่ยวข้อง:** `static/drugsearch.js` (ใหม่), `app.py` (`search_drugs` และ API `GET /api/pharmacist/<id>/drugs`),
`templates/chat.html` (ฟอร์มใบสั่งยาในหน้าแชทของเภสัชกร), `static/src/app.css` และ `static/app.css` (สไตล์ของรายการผลค้นหา)
**โครงสร้างฐานข้อมูล:** ไม่เปลี่ยน

### 2. กรณีระบบปฏิเสธคำสั่งซื้อ — บันทึกเป็นสถานะ `rejected` แทนการหายเงียบ

**ปัญหาเดิม:** ถ้าสั่งซื้อไม่ผ่าน (เช่น สต็อกไม่พอ) ระบบ ROLLBACK ทั้งหมด ทำให้ในฐานข้อมูลไม่เหลือร่องรอยเลยว่าคนไข้เคยกดสั่งซื้อ

**สิ่งที่แก้:**
- งานหลักยัง ROLLBACK เหมือนเดิม (สต็อกไม่ถูกตัด ไม่มี `order_detail` ค้าง)
- จากนั้นระบบเปิด transaction ใหม่บน connection ใหม่ บันทึกแถวใน `orders` ด้วยสถานะ `rejected`
  (คนไข้ ใบสั่งยา และที่อยู่จัดส่งที่กรอก) แล้ว COMMIT เพื่อเป็นหลักฐานว่าคนไข้กดสั่งแล้วแต่ถูกปฏิเสธ เหตุผลไม่ได้เก็บในฐานข้อมูล
- บันทึกเฉพาะกรณีที่ระบบปฏิเสธ (สต็อกไม่พอ หรือ error จากฐานข้อมูล เช่น ผิด CHECK/UNIQUE/FK)
  ไม่บันทึกกรณีกรอกข้อมูลผิด (ที่อยู่ว่างหรือยาวเกิน 500, ไม่พบใบสั่งยา, ใบสั่งยาถูกสั่งไปแล้ว)
- ถ้าการบันทึกแถว `rejected` เองล้มเหลว ระบบ log ไว้แล้วแจ้ง error เดิมต่อ
- หน้าเว็บแสดงเหตุผลที่ถูกปฏิเสธ และมีป้าย "ถูกปฏิเสธ" ในประวัติคำสั่งซื้อ
- คนไข้สั่งซื้อใหม่จากใบสั่งยาเดิมได้ เพราะคำสั่งซื้อที่ถูกปฏิเสธไม่ล็อกใบสั่งยา

**การเปลี่ยนในฐานข้อมูล** (`migrations/001_orders_rejected.sql`):
- เพิ่มค่า `'rejected'` ใน CHECK ของสถานะ (`chk_orders_status`)
- เปลี่ยน `uq_orders_prescription` จาก UNIQUE constraint เป็น unique index แบบมีเงื่อนไข (ชื่อเดิม)
  เพื่อให้ 1 ใบสั่งยามีคำสั่งซื้อที่ไม่ถูกปฏิเสธได้ไม่เกิน 1 รายการ:

```sql
CREATE UNIQUE INDEX uq_orders_prescription
  ON orders (CASE WHEN status <> 'rejected' THEN prescription_id END);
```

**การเปลี่ยนในโค้ดที่อ่าน `orders`:**
- คิวรีที่ตรวจ "ใบสั่งยาถูกสั่งไปแล้ว" ใน `place_order` และคิวรีที่ผูกใบสั่งยากับคำสั่งซื้อ (หน้าหลักคนไข้, หน้าใบสั่งยา)
  ไม่นับแถว `rejected`
- คำสั่งซื้อ `rejected` ชำระเงินไม่ได้และไม่มีใบเสร็จ: `pay_order` ปฏิเสธ และหน้าชำระเงิน/ใบเสร็จส่งกลับไปหน้าประวัติคำสั่งซื้อ

**ไฟล์ที่เกี่ยวข้อง:** `transactions.py` (`RejectedError`, `_run`, `_record_rejected_order`, `_raise_out_of_stock`,
ปรับ `place_order` 2 จุด คือเงื่อนไข `status <> 'rejected'` ของการตรวจสั่งซ้ำ และบรรทัด `return _run(...)`, ปรับ `pay_order`),
`app.py`, `templates/orders.html`, `templates/patient_home.html`, `templates/prescription.html`, `migrations/001_orders_rejected.sql`

### วิธีทดสอบกรณีปฏิเสธ
1. ตั้งสต็อกยาให้น้อยกว่าที่ใบสั่งยาขอ (เช่น สต็อก 3 ใบสั่งยา 5)
2. คนไข้กดสั่งซื้อ → หน้าเว็บขึ้นข้อความปฏิเสธ
3. ตรวจในฐานข้อมูล: `orders` มี 1 แถวสถานะ `rejected`, `order_detail` ไม่มีรายการ, `drug_batch.quantity` ยังเท่าเดิม
4. เติมสต็อกแล้วสั่งซ้ำจากใบสั่งยาใบเดิม → ต้องสำเร็จ (ได้แถว `pending_payment` เพิ่ม)

ขั้นตอนนี้อยู่ใน `test_flow.py` (รอบที่ 2) แล้ว

### ข้อสังเกต
- เลขที่คำสั่งซื้อจะข้าม 1 เลขทุกครั้งที่มีการปฏิเสธ (Oracle sequence ไม่ย้อนกลับเมื่อ rollback แถว `rejected` จึงได้เลขถัดไป)
